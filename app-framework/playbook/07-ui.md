# 07 · UI

**Goal:** a page inventory and a page pattern that every Builder follows: verdict first, drill down
by id, clear states, persona-aware, accessible at three widths, with an honest demo mode.
**Owner:** Coordinator · **Approver:** the user (per page)

## When to run / skip

- **Run** once for the app (inventory, patterns, tokens), then **per page** before it is built.
- **Light version** for a small UI tweak: plan in one line, ask one question with 2–3 options,
  then build.
- **Skip** for back-end-only work.

## Inputs

- Persona Sheet (questions, concerns, vocabulary, sort order, persona UI choice V5).
- PRD (P0 pages, acceptance criteria, browsers Q8), data model (ids, retention tiers).
- Brand palette, if any (G7).

## Steps

1. **Draft the page inventory** (G1): landing pages first, then detail pages, in build order.
   Each becomes one Board row. One page per build step.
2. **Per page, before building:** run the persona review from [02](02-personas-value.md): "what
   would <persona> find concerning here?" List concerns with data availability, ask, then plan.
3. **Pick 3–5 key numbers or verdicts** for the top of each page (G2). Give an answer, not raw
   figures: "Room to grow: 12 free", not "Used: 38 of 50".
4. **Landing vs detail:** a landing page ranks and flags; a detail page explains one item. No more
   than two levels of disclosure: key figures first, detail on demand.
5. **Links by id** (G3): every entity name links to its detail page and to the source system.
6. **Persona switch** (V5, G14): an "All" bar plus one card per persona with a headline; sections
   tagged per persona; the choice shared across pages and remembered per browser.
7. **States** (G6): loading skeletons; an empty state that says what to do next; an error with
   retry; an "as of <time>" stamp linked to the diagnostics page (G13).
8. **Charts vs tables** (G8): table first, charts for trends and shares. Use length or position
   (bars, lines); avoid pies, gauges and 3D. Color for categories, not quantities; colorblind-safe;
   one stable color per category across pages (G7).
9. **Filters** (G9, G10): global filters in the URL; time ranges that match the retention tiers,
   with summarized periods labelled "Summarized".
10. **Admin-only controls** (G11) are hidden for others. The server still enforces.
11. **Widths and accessibility** (G5): test at ~1280 / 900 / 420 px. WCAG 2.2 AA: contrast,
    keyboard, labels, focus not hidden, targets at least 24×24 px. The GUI Tester checks each page
    with scripted Playwright sweeps in real Chrome (widths × personas × demo/live); see
    [10 Verify](10-verify.md#scripted-browser-testing-with-playwright).
12. **Tokens and components:** a small set of design tokens (color, type, spacing) and a component
    inventory. Builders reuse; they don't invent.
13. **Demo mode** (G4): an explicit toggle and a visible "Demo data" badge. Values may be made up;
    every field and signal must be one the real system produces today (or before the demo).
    Otherwise remove it or label it "not available yet". Enforce with a demo-data audit test.
14. **Tours** (G12), if there is a demo: one short tour per persona, each step opening its page by
    id, matching the demo script step for step (≤ 8 steps, ≤ 2 sentences each).
15. **Review with Nielsen's 10 heuristics** before sign-off. Log decisions. Close.

## Artifacts produced

- Page inventory on the Board, one row per page ([templates/board.md](../templates/board.md)).
- Per-page plan: key numbers, persona concerns with data availability, drill-downs, states.
- Tokens and component inventory (in the repo, e.g. `docs/ui.md` plus the token file).
- Demo-data audit test and, if needed, tour and demo script (by the Docs Writer).
- Decision Log entries.

## Agent roles involved

- [Coordinator](../agents/coordinator.md): plans each page as the domain specialist.
- [Builder](../agents/builder.md): builds one page per task.
- [GUI Tester](../agents/gui-tester.md): sweeps at three widths, persona × page, demo and live.
- [Docs Writer](../agents/docs-writer.md): demo script and tour text.

## Gate / definition of done

- [ ] G1–G5 answered and logged.
- [ ] Each page has 3–5 key numbers or verdicts agreed before it is built.
- [ ] Every entity link uses an id.
- [ ] Empty, loading, error and stale states exist on every page.
- [ ] Layout passes at three widths with no sideways scroll, clipped names or cut tooltips.
- [ ] WCAG 2.2 AA essentials pass; heuristic review done.
- [ ] Demo data passes the audit test.

## Rules and anti-patterns

- **Verdict first.** Why: an overview that only showed figures failed; users need a direct answer.
  Lesson: r1 §3 (answer first).
- **One page per turn, then stop.** Why: the user reviews each page before the next; a big batch
  hides mistakes. Lesson: r1 §1.2.
- **Demo data must be real-shaped.** Why: the demo showed per-scope pools that can't exist and a
  "disabled" flag read from the wrong field, which misled the audience. Lesson: r1 §1.9.
- **Persona switch, not persona pages.** Why: one page with reordering and highlights keeps the
  numbers consistent for everyone. Lesson: r1 §3 (persona switch).
- **Layout breaks at mid widths; test three.** Why: most layout bugs showed at the middle width.
  Lesson: r1 §6 (scripted browser sweeps).
- **Progressive disclosure, two levels at most.** Why: glanceability. Practice:
  https://www.nngroup.com/articles/progressive-disclosure/
- **Bars and lines, color for categories.** Why: length and position are read accurately; pies and
  gauges aren't. Practice: https://www.nngroup.com/articles/dashboards-preattentive/
- **WCAG 2.2 AA is the baseline.** Why: legal and usability floor, hard to retrofit. Practice:
  https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/
- **Heuristics as the review rubric.** Why: fast and well known. Practice:
  https://www.nngroup.com/articles/ten-usability-heuristics/
- **Design tokens.** Why: consistent UI across pages built by different agents. Practice:
  https://www.designtokens.org/
- **Agents check layout with screenshots.** Why: otherwise they are blind to layout. Practice:
  https://code.claude.com/docs/en/best-practices
- **Anti-pattern: wording that works against the business.** Use the vocabulary list; tests can
  grep for banned words. Lesson: r1 §1.8.
