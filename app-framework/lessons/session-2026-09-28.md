# Session loop, 2026-09-28

The loop below was locked on a live app on 2026-09-27 and 2026-09-28 while a coordinator, planners, two builders, and a cross-model reviewer were already in use. The rules are generic. Each app keeps its own locks in its own decision log.

## The ten rules

1. **Two layers.** The door file (`CLAUDE.md` or `AGENTS.md`) holds stable rules. The Board holds live state. One fact has one home. Other entry files point at the door. They do not restate it.
   - Why: two copies of a rule drift, and the next session follows the stale one.

2. **A written plan before a builder.** Before any change that is not trivial, and before briefing a builder, a planner writes a plan file. Trivial means a one-line fix, a docs edit, or a scratch script. A spec counts as a plan. The plan names files, the done-check, and what stays. It does not authorize code by itself.
   - Why: a chat paragraph disappears, and a builder that starts from it edits the wrong files.

3. **Cross-model review before approval and before merge.** A reviewer from a different model family than the writer reviews every plan and every builder diff. The writer does not review its own family. A cheaper fallback model does not waive that. Verdicts are APPROVE, APPROVE AFTER FIXES, or REJECT. A major sends the writer back. Do not build from REJECT, or from APPROVE AFTER FIXES, until the fix is reviewed again and approved.
   - Why: the writer's own family repeats the writer's blind spots, and an unfixed major still ships.

4. **An approved plan may end with no builder.** If the row is already true, or a code change is not worth it, the plan says so. The coordinator closes the row. An empty builder seat is not a reason to invent the change.
   - Why: an open seat gets filled with work nobody asked for.

5. **Ask only when the user must act or choose.** The request is a question pane: a select, recommendation first and marked, worded so the user can answer without the chat. A paragraph is not the request. Do not assume they read the chat. The Board is the plan, not a place to ask. Work that does not need them keeps moving the same turn. Review closes gaps in a plan. Those gaps are not questions for the user.
   - Why: a paragraph in chat is easy to miss, and a gap the review can close is not the user's job.

6. **Five agents, two builders.** Every turn, count who is actually running. If fewer than five, start the next Board rows that do not share files and do not need the user. Builder seats stay two. The other seats are plans and reviews. Do not invent work, deploy, restart, or break a lock to fill the count. If no safe row is left, say that on the Board.
   - Why: idle seats stall the queue, and a third builder collides on shared files.

7. **The builder does not edit the tree the running app serves.** It works in its own worktree and commits on its own branch. The coordinator merges after the diff review. When the dev server serves the work checkout, a UI merge is what the screen shows. When the server process loads a deployed or pinned tree, a reviewed merge is not live until a separate restart OK. Enabling a schedule and cutting over a behavior are separate OKs. A crash reloads the deployed tree, not the dev checkout, when those trees are split. The plan names which tree is which.
   - Why: a merge into a checkout the process does not load looks done and is not running.

8. **A new label does not rewrite stored history.** New rows use the new label. Reports about the old window read the record as written. A correction pass is its own decision.
   - Why: rewriting old rows makes past reports disagree with the store.

9. **Same-turn memory.** Finished work moves to the history log, newest first. The Board drops that row the same turn. The WIP header count matches the WIP table. A subagent brief names the door file, the row, the decisions that bind it, the output path, and the message to return. Subagents do not see the chat.
   - Why: a stale Board row, or a brief that assumes the chat, sends the next agent the wrong job.

10. **App locks stay in that app.** Irreversible actions, schedules, and cutovers are decision-log entries for the app. The framework states the pattern (separate OK, no history rewrite, name the crash tree). It does not carry another app's locks.
    - Why: a framework that copies one app's locks misleads the next app.

11. **File ownership.** A builder starts only on files no other running agent owns. A second plan may be written. Its builder waits.
    - Why: two writers in one file overwrite each other.

12. **The brief wins.** After APPROVE, the coordinator brief restates the files, the served tree, and the crash tree. The builder follows the brief when an older sentence in the plan still says no builder.
    - Why: the plan was written before approval, and its closing hold is easy to skim as a permanent ban.

13. **A wrong tree is a major.** The plan names which tree the running app serves and which tree a crash loads. A reviewer treats a missing or wrong tree as a major.
    - Why: a builder that edits the served tree, or a plan that names the wrong restart target, ships the change into the wrong process.

14. **Merge is not release.** A reviewed merge is live only for the process that loads that tree. A restart, enabling a schedule, and cutting over a behavior are each a separate OK.
    - Why: a green merge is not the same as the process the user is running.

15. **A standing red-team checkpoint runs as parallel personas, not one reviewer pass.** When a decision requires checking a change against several stakeholder views (an investor-persona, operator-persona, etc. decision log entry), spawn one subagent per named persona instead of one agent asked to "review from all angles." Brief each subagent with: (a) that persona's defining decision entry, (b) the concrete actions or diff under review, written in plain language, (c) 3-4 targeted questions for that persona to answer, ending with "the one sharpest question you'd ask the supervisor." Run all persona subagents in parallel, on a cheap model. The coordinator reads all of them back and synthesizes one set of findings and questions.
    - Why: three personas run in parallel each stayed in their own lane and produced sharp, non-overlapping criticism (capital-at-risk framing, execution-edge specifics, change-management and rollback gaps); a single "review everything" pass earlier in the same session had produced softer, more generic findings by comparison.
    - **Two persona groups, two kinds of question.** Domain personas (who the app is for and what
      breaks their trust — investor/user/operator-shaped, drawn from the app's own Persona Sheet,
      [templates/persona-sheet.md](../templates/persona-sheet.md)) answer questions about the
      app's behavior, risk, and readiness. Technical personas (backend specialist, frontend
      specialist, security specialist — generic, not app-specific) answer questions about
      dev-process and implementation risk: architecture, attack surface, rollout and rollback.
      Pick the group by the question, not the other way round. The technical group needs no
      per-app template entry — it is generic by design; only the domain group is drawn from the
      app's own personas.

Blank forms for rules 2, 3, and 13: [templates/plan.md](../templates/plan.md) and [templates/review-verdict.md](../templates/review-verdict.md).
